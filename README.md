# 프로젝트 배경 및 진행 과정

## 동기

Java를 배운 지 약 3개월쯤 되었을 때, 처음으로 **API 데이터 수집**에 도전했습니다.  
당연히 코드에는 여기저기 허점이 많았고, 그 점을 감안하고 봐주시면 감사하겠습니다.

이 코드는 처음부터 완성도 높은 실제 프로젝트용 모듈로 개발된 것이 아니라,  
어디까지나 **"나만의 실험용 code snippet"** 으로 출발했습니다.  
그래서 일반적인 자바 개발 패턴과는 맞지 않거나 어색한 부분이 많을 수 있습니다.

그럼에도 불구하고 이 **날것 그대로의 코드**를 GitHub에 공개한 이유는 두 가지입니다.

1. 비록 거칠었지만, 이 시도를 통해 **데이터 핸들링의 흐름**을 직접 체감할 수 있었고, 그 경험을 기록으로 남기고 싶었습니다.  
2. 저처럼 자바를 막 배우는 개발자 중에서도 비슷한 시도를 하며 참고할 사람이 있을 수 있다고 생각했습니다. (실제로 그런 분을 한 명 만났습니다!)

***

## 진행 과정

이 시도는 **KDT 중간 프로젝트 - “MoA 공연/전시 게시판”** 개발 중 진행되었습니다.  
당시 고민은 다음과 같았습니다:

> “게시판에 쓸 데이터를 직접 mock으로 만들까,  
> 아니면 실제 전시 데이터를 불러올까?”

그때 **한국문화정보원**에서 여러 기관의 전시 데이터를 **통합 API**로 제공한다는 사실을 알게 되었고,  
*"이미 정제된 clean 데이터겠지"* 라는 기대감에 공공데이터를 직접 활용하기로 결정했습니다.  

하지만 실제로 데이터를 분석해보니 전혀 그렇지 않았습니다.

- 데이터는 **10년 이상** 누적되어 시기별 관리 방식이 크게 달랐습니다.  
- **20개 이상의 기관** 데이터를 통합하다 보니, 동일 필드라도 이름·설명 방식·길이 등이 제각각이었습니다.  
- 결과적으로, **DB에 바로 넣어 쓸 수 있는 수준으로 정규화돼 있지 않았습니다.**

이런 문제는 초기 ERD 설계 시 데이터의 **통계적 특성(분포, 길이, 결측 등)** 을 충분히 고려하지 않았기 때문에 발생했습니다.

***

## 문제 해결 과정

처음엔 수십 개 샘플만 보고 “나머지도 비슷하겠지”라 가정했지만, 곧 잘못된 판단임을 깨달았습니다.  
이후 Python으로 전시 데이터 전체를 **통계적으로 분석**하여 각 필드의 특성을 파악하고,  
그 결과를 **ERD 수정**에 반영했습니다.

그 덕분에 DTO와 DB 컬럼 매핑이 훨씬 매끄러워지고,  
데이터 삽입 프로세스도 큰 문제 없이 완료할 수 있었습니다.

이 경험을 통해 배운 점은 명확했습니다.

>  **“DB 설계는 데이터의 실제 통계적 특성을 이해하는 것에서 출발해야 한다.”**

## 한국문화정보원 외_전시정보(통합) API 데이터 설명: 
- 문화체육관광부 소속/공공(유관) 기관에서 개별 운영 중인 전시 정보를 연계 / 통합하여 "제목(TITLE), 기간(PERIOD), 시간(EVENT_PERIOD), 장소(EVENT_SITE), 관람시간(DURATION), 관람료 및 할인정보(CHARGE)" 등 총 24개 메타데이터 칼럼(COLUMN_ID) 정보를 공통 항목으로 표준화하여 제공하는 데이터셋.<br>
- 참여기관(2024년도 기준): 오픈 API를 구성하는 27개 기관- 국립중앙박물관,국립경주박물관, 국립공주박물관, 국립광주박물관, 국립극단, 국립김해박물관, 국립대구박물관, 국립박물관문화재단, 국립부여박물관, 국립아시아문화전당, 국립어린이청소년도서관, 국립오페라단, 국립익산박물관, 국립제주박물관, 국립중앙극장, 국립진주박물관, 국립청주박물관, 국립춘천박물관, 국립한글박물관, 국립현대무용단, 국립현대미술관, 대한민국역사박물관, 예술의전당, 태권도진흥재단, 한국영상자료원, 한국예술종합학교, 한국체육산업개발(주)
- 이외에 전시정보 자원에 대한 API 원천데이터 표준화가 계속 진행 중이며, 상시 업데이트 된다.<br>
